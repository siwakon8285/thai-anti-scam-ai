# Regression Specification V0.1

จัดทำใน TASK-005-R3 · Contract อนุมัติใน TASK-005-R6 · Dataset version `v0.1`

## Contract Summary

ใช้สัญญาต่อไปนี้เป็นฐานกำหนดผลคาดหวังก่อนพัฒนา Runtime [Behavior Specification](v0.1-behavior.md) · [Rule Architecture](v0.1-rule-architecture.md)

- รับ built-in str แบบ exact type ชนิดอื่นรวม str subclass ได้ TypeError ตรวจอักขระดิบจากซ้ายไปขวาก่อน trim หากพบ surrogate, Cc นอกกลุ่ม TAB/LF/CR หรือ Bidi_Control ให้ ValueError พร้อมเหตุผลและตำแหน่งตัวแรก Bidi_Control ใช้ชุด UCD 16.0.0 ที่ระบุใน R2 อักษร RTL ปกติผ่านขั้นตรวจ
- จัดข้อความว่างหรือข้อความที่มีเพียง whitespace ที่ผ่าน Validation เป็น EMPTY_INPUT ส่วน format-only ต้องมีอย่างน้อยหนึ่งอักขระใน General_Category=Cf หรือ property Variation_Selector ที่ผ่าน Validation และทุกอักขระต้องอยู่ในสองกลุ่มนี้หรือ whitespace ที่อนุญาต จึงได้ UNKNOWN แบบ no-match สระหรือ combining mark ทั่วไปไม่มีสถานะ format-only โดยอัตโนมัติ
- เก็บ Raw Text ชั่วคราวและตรวจ Matching View ด้วย strip() + NFC คง BOM, ZWSP, joiners, variation selectors, เครื่องหมายและข้อความส่วนท้าย รูปสระอำกับรูปแยกยังต่างกันตาม R1 กรณีข้อความยาวตรวจการคงข้อความโดยยังไม่มีเพดานตัวเลข [ผล R1](v0.1-thai-text-processing.md)
- Result Contract ที่อนุมัติใช้ frozen dataclass พร้อม Runtime Validation สำหรับผลสาม field กฎที่ชนะใช้ rule_id ของกฎนั้น รวม HELP ที่เกิดจากกฎและ explicit UNKNOWN ส่วน EMPTY_INPUT, no-match, format-only และ ambiguity ใช้ None ซึ่ง Adapter serialize เป็น JSON null ข้อผิดพลาดภายในต้องส่งต่อโดยรักษาสาเหตุ

ตรวจ Dataset เดิมทั้ง 32 ตัวอย่างผ่านการทบทวน Input Policy และถอด Raw Input กับ Expected Intent ลงกรณีอ้างอิงครบ รวม 004, 006, 007 และ 021 กรณี UNKNOWN จาก Dataset ใช้ Configuration ของ Regression ที่สมมติว่าไม่มี explicit UNKNOWN rule ส่วนการทำงานเมื่อมี explicit rule ตรวจใน Resolver Fixture แยก [Development Dataset](../datasets/development/v0.1.json)

## Regression Schema

ไฟล์ UTF-8 กำหนด version, response_templates และ cases แต่ละ Case มี case_id, requirement_ids, category, status, fixture และ rationale ใช้ source_scenarios และ source_sample_id เพื่อย้อนกลับหลักฐาน same_result_as เปรียบเทียบทั้งสาม field กับ Case อ้างอิง ส่วน follow_up_case ให้ทดสอบการเรียกครั้งถัดไป เช่น หลังกล่าวลา [Regression Dataset](../datasets/regression/v0.1.json)

| ส่วน | รูปแบบ |
| --- | --- |
| Mandatory | มี expected_outcome เพียงรูปแบบเดียว เช่น result, exception, matching_view, manual_review หรือ serialization |
| Pending | มี open_decision อ้าง Q-ID และไม่มี expected_outcome ไม่นับใน Mandatory Coverage |
| ข้อความหรือชนิดข้อมูล | text ให้ built-in str ตามตัวอักษร, json_value ใช้ชนิด JSON เดิม, bytes_hex ให้ bytes.fromhex(), str_subclass ใช้ subclass ขั้นต่ำที่ทดสอบกำหนดเอง, code_points ใช้ chr() ตามรายการจำนวนเต็มและ join สำหรับ surrogate |
| Resolver | candidates ระบุรหัสใน fixture, Intent, Priority, Specificity, guard, หลักฐานว่าเป็นคำทักนำ และการตรวจ permutation ส่วน fault กับ invalid_configuration ระบุเงื่อนไขที่จะฉีดจาก Test Harness |
| Result | ระบุ Intent, path, response_template และเงื่อนไข must_reference_winning_rule หรือ must_be_none ใช้ winning_candidate เฉพาะผู้ชนะใน Resolver Fixture รหัสใน fixture มีไว้ตรวจลำดับภายใน Intent |
| Exception | ระบุ exception type, reason และ code_point_offset เมื่อเกี่ยวกับตำแหน่งอักขระ Input Case แยกจาก Internal Error Fixture และไม่มี expected Intent |
| Matching View / Response | ระบุ Matching View แบบ exact และ assertions สำหรับ Raw/idempotence ส่วน Response มี fixture สำหรับทบทวนความหมาย, ผลผิดโครงสร้าง และสาม field ที่ serialize |

สร้าง fixture จากค่าที่อนุญาตโดยตรงและห้าม eval สตริง JSON ต้องประกอบด้วย Unicode scalar values ส่วน surrogate เก็บเป็นรายการจำนวนเต็ม ตัวตรวจใต้ tests/ ใช้ Strict JSON Parser เดิม ตรวจ duplicate keys ทุกระดับ และตรวจรูปแบบ เงื่อนไขซ้ำ และผลขัดแย้งเมื่อสลับลำดับ Candidate [Specification Validator](../tests/regression_spec_validation.py)

Specificity ยึดระดับหลักฐานของ R2 โดย 2 คือเจตนาตรงพร้อมตัวระบุเพิ่มเติม 1 คือเจตนาตรงที่มีหลักฐานครบ และ 0 คือสัญญาณกว้างที่ผ่าน guard แล้ว ลำดับใน Intent เดียวใช้ Priority → Specificity → ASCII rule_id นอก Intent ใช้เงื่อนไข precedence ที่ประกาศชัดหรือ ambiguity fallback Fixture ระบุความคาดหวังของผู้ชนะโดยไม่เรียกกฎตัวจริง [Scenario และ Decision Table R2](v0.1-rule-architecture.md)

## Response Rubric

กำหนดถ้อยคำ deterministic ต่อ Intent และแยกข้อความสำรองตามสาเหตุ ชุดที่เจ้าของอนุมัติใน JSON ใช้อ้างอิง Behavioral Tests ตัวตรวจอัตโนมัติตรวจ Taxonomy, ข้อความที่ไม่ว่าง, path, Template reference, ความสัมพันธ์ของ rule_id และ wire fields ผู้ทบทวนตรวจความหมายเต็มประโยคจาก manual_review fixtures ทั้งตัวอย่างที่ควรรับและควรปฏิเสธ

- BOT_IDENTITY ต้องระบุ thai-anti-scam-ai และอธิบายว่าเป็นต้นแบบบอตภาษาไทยแบบใช้กฎ
- HELP ต้องขอรายละเอียดหรือให้จุดเริ่มต้นที่รองรับ หลีกเลี่ยงการวินิจฉัยหรือรับปากว่าช่วยไปแล้ว
- BOT_CAPABILITIES ต้องบอกขอบเขตตามจริงและระบุว่ายังตรวจจับการหลอกลวงไม่ได้ UNKNOWN ต้องสื่อข้อจำกัดหรือชวนระบุคำขอโดยไม่แต่งข้อมูลหรือกล่าวหาบุคคล คำตอบที่มี Keyword ตรงแต่อ้างความสามารถผิดให้ Reject

R4–R5 ทบทวน 11 Template records สำหรับ 8 Intent ส่วน R6 ใช้ถ้อยคำ BOT_CAPABILITIES และ UNKNOWN แบบ ambiguity ตามผลอนุมัติ โดยรักษา Template อื่นและปรับตัวอย่าง manual_review ที่อ้างถึงให้ตรงกัน BOT_CAPABILITIES เป็นถ้อยคำที่กำหนดสำหรับ V0.1 เมื่อ Runtime รองรับตามข้อกำหนด [Response Templates](../datasets/regression/v0.1.json)

Frozen dataclass เหมาะกับผลที่มีสาม field แบบ scalar เพราะลดการแก้ค่าโดยบังเอิญและเปรียบเทียบผลซ้ำได้ ให้ตรวจชนิดและค่าขณะสร้างผล และตรวจ rule_id เทียบเส้นทางกับกฎที่ชนะในขั้นที่ยังมีข้อมูลดังกล่าวก่อนคืนผล Adapter จึงแปลง None เป็น JSON null ได้โดยรักษาความหมายเดิม [Python dataclasses](https://docs.python.org/3.14/library/dataclasses.html#frozen-instances)

แตก Mandatory IDs ที่อนุมัติเป็น Executable Tests และงานทบทวนความหมายโดยคนตามประเภท fixture กำหนด oracle ล่วงหน้าและเก็บ RED ของแต่ละส่วนจากพฤติกรรมที่ยังขาด เมื่อรันซ้ำให้ตรวจเซต ID ที่รันจริงเทียบทั้งชุด รวม permutation และ follow-up ตาม fixture รายงาน Test Methods, Behavioral Cases และ Manual Reviews แยกกัน Mandatory ที่หาย, Skip หรือ Expected Failure ทำให้เกณฑ์ยังไม่ผ่าน Mock Engine ไม่ใช้แทน Engine จริง ทดสอบส่งต่อ Internal Error ด้วยการฉีดความผิดพลาดที่ขอบเขตส่วนงาน แล้วรัน Regression เดิมและรายงาน Development Accuracy แยกจากผลผ่านชุดทดสอบ การเปลี่ยน Expected Outcome ต้องผ่าน Review แยกจากการแก้โค้ด

R6 อนุมัติเพดานชั่วคราว **32,768 raw Unicode code points** สำหรับข้อความสมมติ เริ่มที่ 128 และเพิ่มตามขนาดใน R1 แจ้งข้อผิดพลาดเมื่อเกินขอบเขตและรักษาข้อความเต็มสำหรับตัวอย่างที่รับ ทดสอบ Regex near-match ใน child process ทีละกรณี ใช้ deadline **2 วินาทีต่อ child process** ให้ parent ยุติและรอเก็บ process เมื่อหมดเวลา แล้วหยุดเพิ่มขนาด เก็บ Pattern ID, ขนาด, เวลา, ผล timeout, peak memory และ Environment แยกรอบวัดเวลาจากรอบ profiling หน่วยความจำ

R5 ตรวจกลไกหยุดด้วย dummy child process ที่ deadline 0.25 วินาที พบ timeout ตามคาด ฆ่าและรอเก็บสำเร็จ (child `-9`, parent Exit `0`, รวม 0.253 วินาที) เพดานและ deadline ที่อนุมัติใช้เฉพาะการทดลอง ส่วน Production Limits ต้องอาศัยผลวัด Engine จริง [Python re](https://docs.python.org/3.14/library/re.html) · [Python subprocess](https://docs.python.org/3.14/library/subprocess.html#subprocess.run)

คำสั่งตรวจ Specification คือ `python3 -B -m unittest -v tests.test_regression_spec` และชุด Local ใช้ `python3 -B -m scripts.run_tests` การตรวจ Matching View เทียบ oracle กับ Python Standard Library ตาม R1 การตรวจ Resolver จำกัดที่ข้อมูลใน Fixture และความสอดคล้องของผลคาดหวัง
