# Rule Architecture และ Response Contract V0.1

ออกแบบใน TASK-005-R2 · เงื่อนไขที่อนุมัติใน R6 อ้างอิง [Regression Specification](v0.1-regression-spec.md)

## 1. Rule Architecture

V0.1 อ่านหนึ่งข้อความและคืนหนึ่ง Intent ตาม Taxonomy เดิม เสนอให้แบ่งขั้นตรวจ Input, สร้าง Matching View, รวบรวม Candidate, ตัดสินผล และสร้างคำตอบ เพื่อให้ทดสอบเงื่อนไขและข้อผิดพลาดแต่ละขั้นแยกกัน

~~~mermaid
flowchart LR
    A[Validate Input] --> B[Classify Blank or Format-only]
    B --> C[Build Matching View]
    C --> D[Match and Apply Guards]
    D --> E[Select Intent]
    E --> F[Render and Validate Response]
    B -->|Early outcome| F
~~~

| แนวทาง | ข้อดีและข้อจำกัด | ข้อเสนอ V0.1 |
| --- | --- | --- |
| First Match | หยุดเร็วและง่ายเมื่อแนวทางไม่ซ้อนกัน แต่ลำดับการลงทะเบียนอาจซ่อน Conflict | ใช้เป็นตัวเทียบในการออกแบบ |
| Explicit Priority | บอกลำดับที่ตั้งใจ ตรวจย้อนกลับได้ การตั้ง Priority กว้างเกินไปอาจให้กฎผิดเจตนาชนะ | ใช้จัดกฎใน Intent เดียว และใช้เงื่อนไขข้าม Intent ที่ระบุแยก |
| Specificity | ให้ความสำคัญกับหลักฐานเฉพาะ แต่จำนวนคำและความยาว Pattern ไม่สะท้อนความหมาย | ใช้ระดับหลักฐานที่นิยามร่วมกันเป็นลำดับรองภายใน Intent เดียว |
| Candidate Scoring | รวมหลายสัญญาณได้ แต่ต้องกำหนดน้ำหนักและวิธีแก้คะแนนเสมอ เกิดผลข้างเคียงเมื่อปรับน้ำหนัก | พิจารณาภายหลังเมื่อมีหลักฐานว่าลำดับที่อธิบายได้ยังไม่เพียงพอ |
| Context Guards | ตัด match จากคำอ้าง คำปฏิเสธ หรือวัตถุคำขอผิดขอบเขตได้ แต่ guard กว้างอาจตัดเจตนาที่ถูกต้อง | ใช้เป็นเกณฑ์เข้าร่วมก่อนจัดอันดับ พร้อมคู่บวก–ลบราย guard |
| Ambiguity Fallback | ขอความชัดเจนเมื่อหลักฐานยังไม่พอ แต่ความกำกวมที่กำหนดกว้างจะเพิ่มการงดตัดสิน | ใช้กับ Candidate ข้าม Intent ที่ไม่มีผลชนะชัดตาม Decision Table |

| วิธี Match | การใช้งานที่เสนอและจุดตรวจ |
| --- | --- |
| Exact Match | เปรียบเทียบทั้ง Matching View เหมาะกับวลีตรงและรูปที่ระบุไว้ ทดสอบคำลงท้ายและข้อความอื่นที่ต่อท้าย |
| Full Match | ตรวจ Pattern ครอบคลุมวลีหรือช่วงที่กำหนดทั้งหมด เหมาะกับโครงสร้างที่มีรูปแปร ตรวจช่วงให้ครบก่อนเลือก Candidate |
| Anchored Pattern | ใช้ขอบเขตข้อความหรือช่วงที่กำหนดชัด ตรวจ CR/LF, ข้อความต่อท้าย และผลของ Regex flags การ match เฉพาะต้นข้อความยังเหลือบริบทส่วนท้าย |
| Substring Match | ใช้เป็นสัญญาณประกอบก่อน guard เช่น ตรวจว่าอยู่ภายในคำอ้างหรือคำปฏิเสธ การพบคำอย่างเดียวไม่พอให้ผ่าน |
| Regular Expression | ใช้เมื่อ literal หรือชุดวลีไม่พอ กำหนด scope และ flags ชัด ใช้ full match หรือ anchors ตามความหมาย หลีกเลี่ยงการใช้ `\b` เป็นตัวแบ่งคำภาษาไทยโดยปริยาย |

R1 พบว่า Regex word chunks แยก “สวัสดีครับ” กลางคำ และ split() ไม่แบ่ง “ภาษาไทย” จึงต้องตรวจขอบเขตวลีจากหลักฐานที่ประกาศในกฎ เสนอให้ใช้ Pattern คงที่ที่ผ่านการทบทวน หลีกเลี่ยง repetition ซ้อน, alternation ที่ซ้อนทับภายใน repetition และ wildcard กว้างที่เพิ่มการย้อนตรวจ ให้ทดสอบ worst-case บนข้อความยาวที่เกือบตรงและข้อความซ้ำก่อนเพิ่มกฎ การ compile และ full match อย่างเดียวไม่ได้จำกัด Worst-case Execution Time ของ Regex [ผล R1](v0.1-thai-text-processing.md) · [Python re](https://docs.python.org/3.14/library/re.html)

## 2. Input Policy

| ประเด็น | ข้อเสนอ | หลักฐานและผลกระทบ |
| --- | --- | --- |
| ชนิดข้อมูล | รับ built-in str แบบ exact type ใน V0.1 และคืน TypeError สำหรับ non-string หรือ subclass ห้าม coercion | ลดความไม่แน่นอนจาก dispatch ที่ override ได้ มีผลต่อผู้เรียกที่ใช้ subclass จึงรอยืนยันและเก็บกรณีทดสอบโดยตรง |
| Invalid Unicode และ Cc | คืน ValueError สำหรับ surrogate ทุกตัวในช่วง U+D800–U+DFFF หรือ Cc นอก allowlist แม้ NUL หรือ ESC จะ encode เป็น UTF-8 ได้ | EXP-002 ยืนยันว่า encode แบบ strict ปฏิเสธ surrogate แต่รับ NUL และ ESC |
| Control allowlist | อนุญาตเฉพาะ TAB U+0009, LF U+000A และ CR U+000D เพื่อรองรับข้อความเว้นวรรค ขึ้นบรรทัด และ CRLF | VT U+000B, FF U+000C และ NEL U+0085 เป็น White_Space แต่เสนอไม่รองรับในต้นแบบเพราะยังไม่มีหลักฐานว่าจำเป็น U+001C–U+001F เป็น Cc ที่ Python ตัดได้และเสนอปฏิเสธเช่นกัน ข้อนี้ปรับข้อเสนอ R1 ที่เคยอนุญาต VT, FF และ NEL |
| ข้อความว่าง | หลัง validate ให้ EMPTY_INPUT เมื่อข้อความว่างหรือประกอบด้วย Unicode White_Space ที่อนุญาตทั้งหมด | บน UCD 16.0.0 เหลือ whitespace ที่อนุญาต 22 จาก 25 ตัว ส่วน Python มี 29 ตัว การตรวจ Cc ก่อน strip ทำให้ Python strip ตัดได้เฉพาะชุดที่ยอมรับ Dataset เดิม 029–032 ใช้สตริงว่าง, space, TAB และ LF จึงคงผลเดิม |
| BOM / ZWSP / joiners / selectors | รักษา U+FEFF, U+200B, U+200C/U+200D และ variation selectors ใน Raw และ Matching View ขั้น decode ของ Adapter จัดการ BOM ของ encoding ตามหน้าที่ | การลบกว้างอาจเปลี่ยนขอบเขตคำหรือรูป emoji ข้อเสนอ format-only คือถ้าไม่มีเนื้อหาอื่นนอกจาก whitespace ที่อนุญาต, Cf ที่ผ่านการตรวจ หรือ Variation_Selector และมีอย่างน้อยหนึ่ง format/selector ให้คืน UNKNOWN แบบ no-match พร้อมชวนป้อนข้อความที่ตีความได้ |
| Bidi formatting | เสนอปฏิเสธ Bidi_Control ตาม UCD 16.0.0 ด้วย ValueError ได้แก่ U+061C, U+200E–U+200F, U+202A–U+202E และ U+2066–U+2069 อักษร RTL เช่น อักษรอาหรับและฮีบรูปกติผ่านขั้นตรวจชนิดอักขระ | จำกัดความเสี่ยงจากการเปลี่ยนการจัดวางที่อาจทำให้ตรวจหลักฐานยาก มีต้นทุนด้าน interoperability กับข้อความ RTL ที่ใช้ controls ตามปกติ จึงรอเจ้าของทบทวน ชนิดอักขระ RTL ตาม Bidi Class เพียงอย่างเดียวไม่มีผลให้ปฏิเสธ [UCD 16.0.0 PropList](https://www.unicode.org/Public/16.0.0/ucd/PropList.txt) · [Unicode Bidirectional Algorithm](https://www.unicode.org/reports/tr9/) |
| Raw และ Normalization | เก็บ Raw ในหน่วยความจำระหว่างการเรียกและสร้าง Matching View ด้วย strip() + NFC หลัง validate ใช้ Raw เป็นตัวเทียบและใช้ตำแหน่งใน Matching View ตามจริง | EXP-001/003 สนับสนุน canonical matching และแสดง collision จาก compatibility folding, casefold หรือการลบเครื่องหมายกว้าง จึงเสนอให้จำกัดวิธีเหล่านั้นไว้เฉพาะกรณีที่มีหลักฐานและกรณีทดสอบ รองรับการอ้างตำแหน่งกลับ Raw เมื่อมีข้อกำหนด |
| ข้อความยาว | ประเมินความยาวดิบด้วย code points เมื่อจะกำหนดเพดาน ปฏิเสธเกินเพดานพร้อมแจ้งข้อผิดพลาดเมื่อมีนโยบายที่อนุมัติ ข้อความตาม Contract ปัจจุบันจึงไม่ถูกตัดทิ้งเงียบ ๆ | EXP-004 วัด string operations เท่านั้น เพดานและพฤติกรรมเมื่อเกินขีดจำกัดรอหลักฐานของ Engine และข้อจำกัด Adapter |

**Error precedence ที่เสนอ** ตรวจ Configuration ก่อนรับงาน จากนั้นตรวจชนิด → ตรวจอักขระดิบจากซ้ายไปขวาและรายงานข้อผิดพลาดแรกโดยระบุเหตุผลกับตำแหน่ง code point → ตรวจ blank/format-only → สร้าง Matching View → เลือก Intent → ตรวจผลตอบ Error ที่เกิดในขั้นภายในแยกจาก ValueError ของ Input และไม่คืนผลบางส่วน ตัวอย่าง space ตามด้วย VT เป็น ValueError แม้ strip แล้วจะว่าง หากเพิ่มเพดานในภายหลัง ให้ทบทวน precedence ของความยาวก่อนเริ่มอ้างเป็น Contract

## 3. Rule Contract

| Field | ความหมายและเหตุผล |
| --- | --- |
| rule_id | รหัสถาวรที่ไม่ว่าง ประกอบด้วย ASCII ตัวพิมพ์เล็ก ตัวเลข จุดหรือขีดกลาง ต้องไม่ซ้ำและไม่ใช้ลำดับค้นพบไฟล์เป็นส่วนหนึ่งของการตัดสิน ใช้ตรวจย้อนกลับและแก้ tie ภายใน Intent |
| intent | หนึ่งใน Taxonomy เดิมสำหรับกฎที่ลงทะเบียน EMPTY_INPUT มาจากการตรวจ Input และ UNKNOWN อาจมาจากกฎเฉพาะนอกขอบเขต |
| matching conditions | ระบุวิธี Match, ข้อความหรือ Pattern และ scope ที่ต้องตรวจ เพื่อบอกว่า Candidate มีหลักฐานอะไร |
| guard conditions | เงื่อนไข boolean ที่ใช้กับข้อความเดียว เช่น ผู้ถูกถาม การอ้างคำพูด และ scope ของคำปฏิเสธ Guard ที่คืน False ตัด Candidate ส่วนข้อผิดพลาดของ guard ต้องส่งต่อ |
| priority | จำนวนเต็มที่ประกาศไว้ ค่าสูงกว่าชนะภายใน Intent เดียว ใช้ค่าเดียวกันเป็นค่าเริ่มต้นของกฎที่ไม่มีเหตุผลต้องจัดลำดับต่าง |
| specificity | ระดับหลักฐานที่ประกาศพร้อมเหตุผล 2 = เจตนาตรงพร้อมตัวระบุเพิ่มเติมที่จำกัดผู้ถูกอ้างถึงหรือรูปคำถาม, 1 = เจตนาตรงที่มีหลักฐานครบ, 0 = สัญญาณกว้างที่ผ่าน guard แล้ว ใช้เมื่อ Priority ภายใน Intent เดียวเท่ากัน |
| response reference | อ้าง Template หรือชุดคำตอบที่ผ่าน Rubric เพื่อทดสอบการเลือกกฎแยกจากข้อความตอบ สถานะ no-match, ambiguity และ empty มีคำตอบสำรองของเส้นทางตนเอง |

Configuration ต้องตรวจรหัสซ้ำ, ค่า Intent, Priority/Specificity และ response reference ก่อนให้บริการ Matching และ guards ให้ผลซ้ำจากข้อความและ Configuration เดียวกันโดยไม่มีผลข้างเคียง ลำดับภายใน Intent คือ Priority มากไปน้อย → Specificity มากไปน้อย → rule_id แบบ ASCII น้อยไปมาก กฎในกลุ่ม tie ต้องรักษา Rubric เดียวกัน การแก้กลุ่มที่มีลำดับเสมอควรตรวจผลที่ชนะจริงใน Regression ไม่ใช้เลข Priority หรือ Specificity บังคับข้าม Intent ที่ยังตีความได้หลายแบบ

## 4. Conflict Resolution

### Eligibility แยกตาม Intent

| Intent | หลักฐานที่ทำให้มีสิทธิ์ | Conflict ที่ต้องตรวจ |
| --- | --- | --- |
| GREETING | คำทักทายที่ส่งถึงบอตเอง | ตัดคำทักที่ถูกอ้าง หากเป็นเพียงคำขึ้นต้นให้คำถามตัวตนหรือความสามารถที่ชัดชนะ |
| BOT_IDENTITY | ถามชื่อ ชนิด หรือตัวตนของบอต | แยกจากการถามว่าทำอะไรได้บ้าง หรือตัวตนบุคคลอื่น |
| BOT_CAPABILITIES | ถามขอบเขตหรือหน้าที่ของบอต | แยกจากการขอความช่วยเหลือโดยตรง แม้มีคำว่า “ช่วย” |
| THANKS | ขอบคุณโดยตรง | การปฏิเสธความช่วยเหลือในอีกช่วงไม่ยกเลิกคำขอบคุณโดยอัตโนมัติ |
| FAREWELL | กล่าวลาเพื่อปิดการสนทนา | แยกคำเล่าหรือคำลาในคำพูดผู้อื่น และไม่มีการปิดโปรแกรม |
| HELP | ขอความช่วยเหลือทั่วไปหรือถามวิธีเริ่มโดยไม่ระบุงานเฉพาะ | ตัดคำปฏิเสธและคำขอเฉพาะนอกขอบเขต |
| UNKNOWN | หลักฐานกฎเฉพาะของข้อความนอกขอบเขต หรือผลสำรองเมื่อขาดหลักฐานเลือก | แยก explicit UNKNOWN, no-match และ ambiguity ตามเส้นทางที่เกิดจริง |
| EMPTY_INPUT | ผลของ Input Validation และ Blank Check | ตรวจหลังปฏิเสธอักขระผิดเงื่อนไข แล้วข้าม Candidate Collection |

### Decision Table

| ID | สถานการณ์ | ผลที่เสนอ |
| --- | --- | --- |
| C01 | Input ผ่าน validation และว่าง / format-only | EMPTY_INPUT / UNKNOWN แบบ no-match ตามลำดับ ทั้งสองกรณี rule_id เป็น None และข้าม matching |
| C02 | Match ผ่าน แต่ guard ไม่ผ่าน | ตัด Candidate ก่อนตัดสินทุกครั้ง แม้ Priority สูงกว่า Candidate อื่น |
| C03 | ไม่มี Candidate ที่ผ่าน หลังตรวจข้อความ valid | UNKNOWN แบบ no-match, rule_id เป็น None |
| C04 | เหลือ Candidate เดียวหลัง guard | ใช้ Intent และ rule_id ของ Candidate นั้น รวม explicit UNKNOWN |
| C05 | หลาย Candidate Intent เดียวกัน Priority ต่าง | ใช้ Priority สูงสุด |
| C06 | Priority สูงสุดเสมอกันใน Intent เดียว แต่ Specificity ต่าง | ใช้ Specificity สูงสุด |
| C07 | Priority และ Specificity สูงสุดเสมอกันใน Intent เดียว | ใช้ rule_id ที่เรียง ASCII ก่อน การสลับลำดับ Candidate ต้องไม่เปลี่ยนผล |
| C08 | ต่าง Intent และมีเจตนาหลักที่ชัดตามเงื่อนไขที่ประกาศ | คำถาม BOT_IDENTITY หรือ BOT_CAPABILITIES ชนะ GREETING ที่เป็นคำขึ้นต้นเพียงอย่างเดียว |
| C09 | ต่าง Intent หลายกลุ่มและไม่มีผู้ชนะเหนือทุกกลุ่มตามเงื่อนไขที่ประกาศ | UNKNOWN แบบ ambiguity, rule_id เป็น None และขอให้ระบุคำขอหลัก ลำดับ rule_id และคะแนนดิบไม่มีผลข้าม Intent |
| C10 | Matching, guard, การเลือกหรือสร้าง/ตรวจ Response เกิด Internal Error | ส่ง exception ต่อโดยรักษาสาเหตุ และไม่คืน Intent, rule_id หรือคำตอบบางส่วน |

เปรียบเทียบเฉพาะผู้แทนที่ชนะในแต่ละ Intent ตาม C05–C07 แล้วใช้ C08 เมื่อผู้แทนหนึ่งกลุ่มชนะคู่แข่งทุกกลุ่มตามเงื่อนไขที่ระบุ หากพบคำถามตัวตนและความสามารถพร้อมกัน ให้ใช้ C09 แม้ทั้งสองจะชนะคำทัก Guard ใช้หลักฐานในข้อความปัจจุบันและตัดสัญญาณที่ถูกปฏิเสธหรืออ้างก่อนเปรียบเทียบ R6 กำหนดผล End-to-end ของ “ขอบคุณครับ ช่วยเริ่มให้หน่อย” เป็น HELP เพราะคำขอเริ่มต้นยังมีผล ส่วน Candidate Fixtures ของ R2 ยังคงทดสอบ precedence ของคำทักนำกับคำถามตรง

## 5. Response Contract

| รูปแบบ | Type safety และ Validation | Mutability / Serialization / การดูแล |
| --- | --- | --- |
| dict | Schema ต้องตกลงและตรวจเองทุกจุดที่สร้าง | แก้ key/value ได้ serialize ง่าย แต่ตรวจการสะกด key และชื่อ field เมื่อเทียบผล |
| TypedDict | กำหนด field และชนิดสำหรับ static checking ค่า runtime ยังเป็น dict และต้อง validate เอง | แก้ได้ตามลักษณะ dict และ serialize ตรง เหมาะเมื่อ API ต้องใช้ mapping |
| Frozen dataclass | ระบุ fields และใช้ validation ตอนสร้างผล Type annotations ไม่บังคับชนิดเอง | ป้องกันการแก้ field ตามปกติและเปรียบเทียบผลตามค่าได้ ใช้ scalar fields ทั้งหมด และให้ Adapter แปลงเป็น JSON keys ที่กำหนด |

ตรวจสามระดับ ได้แก่ field และชนิดครบ, การเลือก Template/ชุดที่อนุมัติแบบกำหนดผลซ้ำได้ และการทบทวนความหมายทั้งคำตอบเทียบกับ Rubric กับข้อห้าม ตัวอย่างคำตอบที่มีคำว่า “ตรวจจับ” อาจสื่อว่าตรวจจับได้หรือยังทำไม่ได้ จึงต้องตรวจส่วนที่ยืนยันและปฏิเสธพร้อมกัน เมื่อข้อความภายในผิด Contract ให้ถือเป็น Internal Error ตาม C10

## 7. Open Design Questions

- **Input Policy** ใช้ exact str, allowlist TAB/LF/CR และการตรวจ Raw ก่อน trim ตาม Regression Spec R6 ระบุ no-match สำหรับ BOM นำคำทัก, ZWSP กลางคำ และ combining mark ล้วน ส่วน ZWSP เดี่ยวอยู่ในเส้นทาง format-only
- **Q-03/Q-05/Q-14** เปรียบเทียบ Matching View กับกรณีไทยเพิ่มเติมและตรวจ span กลับ Raw ส่วน Input Limit และ Regex worst-case รอวัดกับกฎจริง
- **Behavioral Tests** ใช้ผลที่อนุมัติรวมคำขอเริ่มต้นร่วมกับคำขอบคุณ, กติกา precedence จาก R2, Result Contract และ Template R6 เป็น oracle ก่อนเขียนกฎจริง
