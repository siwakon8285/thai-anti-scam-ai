# การวิเคราะห์ Behavioral Contract และ Regression Engineering V0.1

สถานะ **ANALYSIS_COMPLETE_PENDING_REVIEW** · TASK-005 · Branch ที่เจ้าของโครงการระบุ design/v0.1-behavioral-contract

## 1. Executive Summary

V0.1 กำหนดการสนทนาภาษาไทยครั้งละหนึ่งข้อความและคืน Intent เดียวจากแปดประเภท งานนี้ระบุความหมายและขอบเขตของแต่ละ Intent ตรวจตัวอย่างเดิม 32 รายการ และแปลงข้อกำหนดเป็นรายการที่ผู้ทดสอบตรวจย้อนกลับได้ กรณีสำคัญก่อน Implementation คือการกล่าวถึงคำพูด การปฏิเสธ ข้อความหลายเจตนา ขอบเขต whitespace และความหมายของ Rule ID เมื่อระบบใช้คำตอบสำรอง

ข้อเสนอเบื้องต้นให้แยกผลสนทนาปกติจากข้อผิดพลาด รักษาข้อความต้นฉบับในหน่วยความจำเฉพาะระหว่างประมวลผล และประเมินคุณภาพ Intent กับความถูกต้องของคำตอบแยกกัน การเลือก Normalization และ Input Length Limit ต้องอาศัยการทดลองเพิ่มเติม ผลปัจจุบันครอบคลุมเอกสาร เครื่องมือประเมิน และพฤติกรรมของ Python Standard Library

## 4. Intent Taxonomy Analysis

### GREETING · BC-INT-01

- **ความหมายและขอบเขต** ผู้ส่งเริ่มปฏิสัมพันธ์กับบอตโดยตรง ครอบคลุมคำทักทายทั่วไป รูปย่อที่ระบุไว้ และคำลงท้ายสุภาพ การกล่าวถึงคำทักทาย รายงานคำพูดของผู้อื่น และการสั่งให้ทักคนอื่นอยู่นอกขอบเขต
- **ตัวอย่าง** บวก “หวัดดี”, “สวัสดีตอนเช้าค่ะ” ลบ “เขาบอกว่าสวัสดี”, “คำว่าสวัสดีแปลว่าอะไร” ขอบเขต “ทักทายครับ” อาจเป็นการทักหรือสั่งให้ทัก ส่วน “สวัสดีครับ คุณคือใคร” มีทั้งการเปิดบทสนทนาและคำถามตัวตน
- **ข้อขัดแย้งและผลตอบ** GREETING อาจแข่งกับ BOT_IDENTITY, BOT_CAPABILITIES หรือ FAREWELL ในบางรูปใช้คำทักเมื่อลา เมื่อตัดสินว่าเป็น GREETING ให้ทักกลับเป็นภาษาไทย
- **FP / FN และ Test** Substring อาจรับคำอ้างเป็นการทัก ขณะที่ exact match ตกคำลงท้ายหรือคำทักตามเวลา ตรวจคู่ทักตรง–อ้างคำพูด คำทักต้นข้อความที่มีคำถาม และรูปย่อที่รองรับ

### BOT_IDENTITY · BC-INT-02

- **ความหมายและขอบเขต** ถามว่าบอตคือใคร ชื่ออะไร หรือเป็นบอตหรือไม่ เป้าหมายคือคู่สนทนาหรือระบบที่กำลังใช้งาน การถามตัวตนบุคคลอื่นหรือลักษณะงานที่ระบบทำอยู่นอกขอบเขตนี้
- **ตัวอย่าง** บวก “คุณคือใคร”, “คุณเป็นบอตใช่ไหม” ลบ “เจ้าของร้านคือใคร”, “คุณทำอะไรได้บ้าง” ขอบเขต “คุณชื่ออะไร” ชัดด้าน Intent แต่ต้องตกลงเรื่องชื่อในคำตอบ “นี่คือบอตอะไร” อาจหมายถึงชนิดหรือหน้าที่
- **ข้อขัดแย้งและผลตอบ** ชน BOT_CAPABILITIES เมื่อคำถามกล่าวถึงชนิดของบอตและชน GREETING เมื่อมีคำทักนำ แนะนำตัวว่าเป็นต้นแบบบอตภาษาไทยแบบใช้กฎของโครงการ ชื่อทางการเป็นเรื่องที่เจ้าของโครงการต้องยืนยัน
- **FP / FN และ Test** คำว่า “ใคร” หรือ “บอต” ทำให้ถามคนอื่นหรือถามความสามารถแล้วถูกจับผิดได้ รูปละประธานอย่าง “ชื่ออะไร” อาจตกหล่น ตรวจผู้ถูกถาม คำถามใช่–ไม่ใช่ และคู่ “บอตอะไร” กับ “บอตนี้ทำอะไรได้บ้าง”

### BOT_CAPABILITIES · BC-INT-03

- **ความหมายและขอบเขต** ถามขอบเขตเชิงข้อมูลว่าระบบทำอะไรหรือรองรับเรื่องใด แยกคำขอให้ช่วยลงมือ คำถามชื่อ และคำขอความรู้เฉพาะทาง
- **ตัวอย่าง** บวก “ระบบนี้รองรับการสนทนาเรื่องอะไร”, “คุณช่วยเรื่องอะไรได้บ้าง” ลบ “ขอความช่วยเหลือหน่อยค่ะ”, “คุณเป็นบอตใช่ไหม” ขอบเขต “คุณตรวจจับการหลอกลวงได้ไหม” เป็นคำถามความสามารถแบบเจาะจงที่สอดคล้องกับนิยาม แต่รูปแบบตอบและการครอบคลุมต้องยืนยัน “ช่วยได้ไหม” อาจหยั่งความสามารถหรือขอให้ช่วย
- **ข้อขัดแย้งและผลตอบ** คำว่า “ช่วย” ซ้อนกับ HELP คำว่า “บอต” ซ้อนกับ BOT_IDENTITY คำตอบอธิบายสิ่งที่ทำได้ใน Runtime ที่กำลังทดสอบและแจ้งข้อจำกัดด้านการตรวจจับการหลอกลวง
- **FP / FN และ Test** การใช้คำว่า “ช่วย” กว้างทำให้จัดคำขอเป็นคำถามขอบเขต รูป “รองรับเรื่องอะไร” อาจตกถ้าคาดเพียง “ทำอะไรได้บ้าง” ตรวจคู่ถาม–ขอ และตรวจความจริงของข้ออ้างในคำตอบทั้งประโยค

### THANKS · BC-INT-04

- **ความหมายและขอบเขต** ขอบคุณคู่สนทนาโดยตรง รวมคำลงท้ายและการระบุเหตุที่ขอบคุณ การประชด การปฏิเสธการขอบคุณ และการรายงานคำขอบคุณของผู้อื่นมีขอบเขตต่างกัน
- **ตัวอย่าง** บวก “ขอบคุณครับ”, “ขอบคุณสำหรับความช่วยเหลือ” ลบ “เขาพูดว่า ‘ขอบคุณ’”, “ฉันไม่ได้ขอบคุณเขา” ขอบเขต “ไม่ต้องขอบคุณครับ” เป็นคำปฏิเสธหน้าที่ขอบคุณ ส่วน “ขอบคุณ แต่ยังไม่ต้องช่วย” แสดงการขอบคุณพร้อมปฏิเสธความช่วยเหลือ
- **ข้อขัดแย้งและผลตอบ** ชน HELP เมื่อกล่าวถึงความช่วยเหลือ และชน FAREWELL เมื่อขอบคุณก่อนลา ผล THANKS ตอบรับคำขอบคุณอย่างสุภาพ
- **FP / FN และ Test** ค้น “ขอบคุณ” อย่างเดียวรับคำอ้างหรือปฏิเสธผิด ขณะที่ตัดคำที่มี “ไม่” ทั้งข้อความอาจพลาดคำขอบคุณจริง ตรวจ scope ของการปฏิเสธและแยก “ขอบใจนะ” จากรูปอ้างคำพูด

### FAREWELL · BC-INT-05

- **ความหมายและขอบเขต** ผู้ส่งกล่าวลาหรือต้องการจบบทสนทนาในข้อความนี้ แยกจากการบอกการเดินทางหรือวางแผนพบกันโดยไม่มีเจตนาลา
- **ตัวอย่าง** บวก “ลาก่อน”, “ขอตัวก่อนนะ” ลบ “เขากล่าวลาก่อนออกจากห้อง”, “สวัสดีตอนเช้าค่ะ” ขอบเขต “ไปก่อนนะคะ” ใช้ลาได้ในบริบทนี้ ส่วน “เดี๋ยวมานะ” อาจเพียงแจ้งว่าจะกลับ
- **ข้อขัดแย้งและผลตอบ** ชน GREETING เมื่อใช้ “สวัสดี” ในการลาและ THANKS เมื่อมีคำขอบคุณนำ กล่าวลาอย่างสุภาพโดยยังรับข้อความถัดไปได้
- **FP / FN และ Test** การเห็น “ไปก่อน” ในประโยคเล่าเหตุการณ์อาจคืน FAREWELL และกฎที่ต้องมี “ลา” อาจพลาด “แล้วพบกันใหม่ครับ” ตรวจคำลาตรงกับรายงานคำลา และตรวจเรียก Engine อีกครั้งหลังคำลาเมื่อมี Runtime

### HELP · BC-INT-06

- **ความหมายและขอบเขต** ผู้ส่งขอความช่วยเหลือทั่วไปหรือทางเริ่มต้นโดยยังไม่มีงานเฉพาะด้าน คำถามขอบเขตเป็น BOT_CAPABILITIES คำขอเฉพาะด้านที่อยู่นอกขอบเขตเป็น UNKNOWN
- **ตัวอย่าง** บวก “ช่วยฉันหน่อย”, “ช่วยแนะนำวิธีเริ่มต้นหน่อย” ลบ “ไม่ต้องช่วยครับ”, “ช่วยบอกสูตรทำขนมครกหน่อย” ขอบเขต “ช่วยด้วยครับ” อาจเป็นคำร้องเร่งด่วนที่ไม่มีรายละเอียด
- **ข้อขัดแย้งและผลตอบ** ชน BOT_CAPABILITIES, THANKS และ UNKNOWN คำตอบเสนอวิธีเริ่มต้นหรือขอรายละเอียด พร้อมตัวอย่างเฉพาะสิ่งที่ทำได้จริง ข้อความกำกวมด้านเหตุเร่งด่วนต้องหลีกเลี่ยงการอ้างว่าดำเนินการช่วยแล้วและรอเจ้าของยืนยัน Rubric
- **FP / FN และ Test** “ช่วย” ในคำขอเฉพาะ คำปฏิเสธ หรือคำขอบคุณทำให้เกิด FP รูป “ขอคำแนะนำหน่อย” อาจตกแม้เป็นคำขอทั่วไป ตรวจคู่ทั่วไป–เฉพาะ ขอ–ถาม และขอ–ปฏิเสธ

### UNKNOWN · BC-INT-07

- **ความหมายและขอบเขต** ผลสำหรับข้อความที่ผ่าน Input Contract แล้วมีเนื้อหานอกขอบเขต หรือมีหลักฐานไม่พอให้เลือก Intent ที่รองรับ Invalid Input และ Internal Error มีเส้นทางของตนเอง
- **ตัวอย่าง** บวก “วันนี้ฝนจะตกไหม”, “ช่วยบอกสูตรทำขนมครกหน่อย” ลบ “ช่วยฉันหน่อย” และสตริงว่าง ขอบเขตข้อความที่มีเพียง emoji หรือ format character ต้องอิงนโยบาย Input ส่วนข้อความหลายเจตนาต้องพิจารณาว่ามีเจตนาหลักที่ชัดหรือไม่
- **ข้อขัดแย้งและผลตอบ** ตัวอย่างสูตรขนมมี Keyword HELP แต่เจตนาอยู่นอกขอบเขต คำตอบแจ้งข้อจำกัดหรือชวนขยายความ หลีกเลี่ยงการแต่งข้อเท็จจริงและการอ้างผลความเสี่ยง
- **FP / FN และ Test** ตั้ง Fallback กว้างเกินไปทำให้เจตนาที่รองรับถูกจัด UNKNOWN ส่วนการจับ Keyword กว้างทำให้ข้อความนอกขอบเขตหลุดไปเป็น Intent อื่น ตรวจ no match, conflict, ข้อความอ้าง และเส้นทางที่ขั้นภายในเกิด Error

### EMPTY_INPUT · BC-IN-02, BC-INT-08

- **ความหมายและขอบเขต** สตริงว่างหรือมีเพียง whitespace ตามนิยามที่ตกลง กรณี Invisible Characters ต้องระบุนโยบายแยก Non-string อยู่นอก Input Contract
- **ตัวอย่าง** บวก สตริงว่าง ช่องว่าง และแท็บ ลบ “สวัสดี” และข้อความที่มีแต่ emoji ขอบเขต NBSP, U+3000, BOM, zero-width space และ whitespace ผสม format character แสดงความต่างระหว่างว่างทางภาพกับว่างตาม Python
- **ข้อขัดแย้งและผลตอบ** ชน UNKNOWN เมื่อข้อความดูว่างแต่ยังมี code point ที่ trim ไม่ออก และอาจชน Invalid Text เมื่อมีอักขระต้องห้าม คำตอบขอให้ป้อนข้อความ
- **FP / FN และ Test** การลบอักขระกว้างอาจทำข้อความมีสาระให้ว่าง การตรวจเฉพาะ ASCII space อาจพลาด whitespace อื่น ตรวจสตริงว่าง แท็บ newline NBSP U+3000 และคู่กับ BOM, ZWJ หรือ NUL ตามนโยบายที่อนุมัติ

## 6. Input Contract Analysis

| Input | ข้อเสนอและเหตุผล | กรณีทดสอบ |
| --- | --- | --- |
| Python str | รับหนึ่งข้อความ พิจารณาว่าจะรับ subclass ที่อาจ override string methods หรือจำกัด built-in str | str และ subclass แบบนิ่ง/override |
| None, int, float, bool, bytes, list, dict | TypeError โดยไม่มี coercion การ decode bytes เป็นหน้าที่ของ Adapter | None, 0, 1.5, False, b'', [], {} และค่าที่ไม่ว่าง |
| Empty / ASCII whitespace | สตริงว่างและ whitespace-only เป็น EMPTY_INPUT | ว่าง, space, tab, LF, CRLF, VT, FF และแบบผสม |
| Unicode whitespace | ใช้ Python strip() เป็นจุดเปรียบเทียบเพราะตรงกับ Dataset Validator พิจารณา Unicode White_Space หรือ subset | NBSP, U+3000, U+0085, U+001C–001F และข้อความที่ล้อมด้วยอักขระเหล่านี้ |
| Combining characters | รับ Unicode scalar values ที่ถูกต้อง เก็บลำดับใน Raw ส่วน mark เดี่ยวอาจคืน UNKNOWN | e + acute เทียบ é, ไทยมีวรรณยุกต์, mark เดี่ยว, canonical order |
| Zero-width / BOM / bidi | รักษา U+200B/U+200C/U+200D/U+2060/U+FEFF ใน Raw งดการลบรวม BOM ตอนอ่านไฟล์อยู่ที่ Adapter ส่วน U+FEFF ใน str เป็น code point หนึ่ง ข้อความ format-only ที่ผ่านการตรวจเสนอ UNKNOWN | format-only, แทรกคำ/ล้อมคำ, U+202E, BOM ต้น/กลาง, emoji ZWJ |
| NUL / Controls | เสนอ ValueError สำหรับ NUL และ controls นอกชุด whitespace ที่ตกลง ระบุการจัดการ U+001C–001F และ U+0085 เพิ่ม | NUL ต้น/กลาง, ESC, DEL, tab/CRLF, controls ผสม whitespace |
| Unpaired surrogate | เสนอ ValueError สำหรับ code points U+D800–U+DFFF ทุกตัวใน Engine str เพราะ strict UTF-8 encode ไม่ได้ แม้เป็นคู่ที่เก็บใน str แบบสอง code points ให้ Adapter decode ก่อน | high/low เดี่ยว, คู่ surrogate แบบสอง code points, scalar เหนือ BMP |
| Emoji / Thai-English | รับ valid text ตามเงื่อนไขเดียวกัน Emoji-only อาจเป็น UNKNOWN และคำอังกฤษไม่ขยายขอบเขต Intent โดยอัตโนมัติ | “👩‍💻”, “สวัสดี 👋”, “สวัสดี Help” และรูปเปลี่ยน case |
| Long inputs | เมื่อมีเพดาน ให้ตรวจ raw ก่อน transform และเสนอ ValueError พร้อมเหตุผลโดยไม่มี raw text | ASCII/ไทย/emoji ที่ N−1, N, N+1, ยาวแต่ trim แล้วว่าง และรูปที่ขยายหลัง normalization |

ลำดับที่เสนอคือชนิด → ความยาว raw → ตรวจ Unicode และ controls → blank → matching → selection → ตรวจผล ยืนยัน precedence ของ Invalid Input ที่มีหลายปัญหาก่อนทำจริง การล้มเหลวใน matching หรือสร้างคำตอบเป็น Internal Error แม้เก็บ Candidate ได้บางส่วนแล้ว

### ความยาวและทรัพยากร

len(str) นับ raw code points และตรวจได้ก่อนสร้างตัวแทนเพิ่ม UTF-8 bytes เหมาะกับงบรับส่งข้อมูลของ Adapter ส่วน grapheme clusters สะท้อนหน่วยที่ผู้ใช้เห็นได้ใกล้กว่าและขึ้นกับวิธี segmentation ภาษาไทยอาจมีสระและวรรณยุกต์หลาย code points ในหน่วยที่เห็นเดียว ถ้ากำหนด N ให้ปฏิเสธทั้งข้อความเมื่อเกิน N การตัดท้ายอาจลบคำปฏิเสธหรือส่วนที่ระบุคำขอ การตัดตาม bytes อาจแยก UTF-8 sequence ต้องทดลอง latency และ peak memory ของข้อความยาวหลายสคริปต์, whitespace ทั้งหมด, combining marks, near-match และรูปที่ขยายหลัง normalization ก่อนเสนอ N หรือเพดานรอง (Q-05, Q-14)

### การทดลอง Python ที่รันจริง

คำสั่ง python3 -B - ผ่าน stdin ด้วยโค้ดด้านล่าง จบ Exit 0 บน Python 3.14.8 / Darwin arm64 / UCD 16.0.0

~~~python
import platform
import unicodedata as u

def points(text):
    return " ".join(f"{ord(ch):04X}" for ch in text) or "-"

print(platform.python_version(), platform.system(), platform.machine(), u.unidata_version)
white = [chr(i) for i in range(0x110000) if chr(i).isspace()]
print("isspace", len(white), points(white))
print("strip agrees for all single code points:",
      all((not ch.strip()) == ch.isspace() for ch in map(chr, range(0x110000))))
print("empty:", "".isspace(), repr("".strip()))
for ch in "\u00A0\u3000\u001C\u0085\u200B\u200C\u200D\u2060\uFEFF\u0000\u001B\u007F\u202E\uD800\uFE0F":
    try:
        ch.encode("utf-8")
        valid = True
    except UnicodeEncodeError:
        valid = False
    print(points(ch), u.category(ch), ch.isspace(), not ch.strip(), valid)
for text in ("e\u0301", "กำ", "ก\u0E4D\u0E32", "Ｈｅｌｐ", "①", "Straße", "👩‍💻", "สวัสดี  Help"):
    print(points(text), "| NFC", points(u.normalize("NFC", text)),
          "| NFKC", points(u.normalize("NFKC", text)),
          "| fold", points(text.casefold()), "| len/UTF-8", len(text), len(text.encode()))
~~~

- isspace() เป็น True จำนวน 29 code points ได้แก่ U+0009–000D, U+001C–001F, U+0020, U+0085, U+00A0, U+1680, U+2000–200A, U+2028–2029, U+202F, U+205F, U+3000 สำหรับสตริงหนึ่ง code point ผลตรงกับการเหลือว่างหลัง strip() ทุกตัว สตริงว่างให้ isspace() เป็น False และ strip() เป็นสตริงว่าง Python อิง general category Zs หรือ bidirectional class WS, B, S โดยรวม U+001C–001F เพิ่มจาก Unicode White_Space [Python Built-in Types](https://docs.python.org/3.14/library/stdtypes.html#str.isspace) · [UCD 16.0.0 PropList](https://www.unicode.org/Public/16.0.0/ucd/PropList.txt)
- U+200B/U+200C/U+200D/U+2060/U+FEFF/U+202E (Cf), U+FE0F (Mn), NUL/ESC/DEL (Cc) มี isspace() เป็น False และ strip() คงไว้ U+D800 (Cs) คงอยู่เช่นกัน แต่ strict UTF-8 encode เกิด UnicodeEncodeError ส่วนอักขระอื่นที่ทดลอง encode ได้
- NFC และ NFKC แปลง e + U+0301 เป็น U+00E9 NFC คง “กำ” เป็น U+0E01 U+0E33 ส่วน NFKC แปลงเป็น U+0E01 U+0E4D U+0E32 ซึ่งตรงกับรูปแยกที่ทดลอง NFKC ยังแปลง “Ｈｅｌｐ” เป็น “Help” และ ① เป็น 1
- casefold() เปลี่ยน “Straße” เป็น “strasse” และเปลี่ยนตัวพิมพ์ใน “สวัสดี  Help” โดยคงช่องว่างทั้งสอง “👩‍💻” มี 3 code points และ 11 UTF-8 bytes ทั้ง NFC/NFKC คงรูปเดิม ผลเหล่านี้แสดงการเปลี่ยน representation ข้อมูลยังไม่เพียงพอจัดอันดับวิธีจำแนก

- rule_id สื่อถึงกฎผู้ชนะที่ทำงานจริง มีชื่อคงที่ข้ามการย้ายไฟล์หรือเรียงกฎใหม่ เก็บทะเบียนรหัสและ version ของกฎ เปลี่ยนรหัสเมื่อความหมายของกฎเปลี่ยนจนการอ้างผลเดิมจะชวนเข้าใจผิด และเลิกใช้รหัสเก่าโดยไม่หมุนไปให้กฎอื่น
- ใช้ None สำหรับ no_match, format_only, ambiguity และ EMPTY_INPUT กรณีที่มีกฎชนะ เช่น HELP หรือ explicit UNKNOWN ต้องอ้างรหัสกฎจริง เมื่อ serialize ให้คง key rule_id และแปลง Python None เป็น JSON null
- Input ผิดชนิดเสนอ TypeError ข้อมูล str ผิดเงื่อนไขเสนอ ValueError ส่วน Internal Error ให้ส่งต่อ หรือตกลง wrapper ที่รักษาสาเหตุและไม่ใส่ raw text ในข้อความผิดพลาด Output ผิด schema เป็น Internal Error และไม่คืนผลบางส่วน Adapter มีหน้าที่แปลงข้อผิดพลาดเพื่อแสดงต่อผู้ใช้
- ภายใต้ Input, Contract/Rule Version, Python/UCD และ Configuration เดิม ให้คืนทั้งสาม field เหมือนเดิม รวมถึง fallback การเปลี่ยน schema แยกจากการเปลี่ยนกฎหรือคำตอบ ระบุรุ่นนอกชุด field ในหลักฐานการทดสอบก่อนพิจารณาเพิ่ม field สาธารณะ

| วิธีตรวจ | ข้อดี | ข้อจำกัดและวิธีใช้ |
| --- | --- | --- |
| Exact Template | ตรวจความคงที่ของถ้อยคำและกรณีที่ต้องใช้คำเดิม | เปราะต่อการแก้สำนวน ใช้กับ Template ที่ตั้งใจ freeze |
| Approved Response Set | รองรับหลายถ้อยคำที่ผ่านการตรวจล่วงหน้า | ต้องทบทวนชุดเมื่อเพิ่มถ้อยคำ และทดสอบ determinism แยกจาก membership |
| Semantic Requirements | ตรวจความหมายและข้อจำกัดตาม Behavior Specification | ต้องมี Rubric และผู้ทบทวนสำหรับผลที่เครื่องตัดสินไม่ได้ เช่น ขอบเขตคำตอบที่อ้างเกินจริง |

ใช้ Rubric ร่วมกับ Template ที่อนุมัติใน R6 การทดสอบตั้งเงื่อนไขที่ต้องมีและข้อกล่าวอ้างที่ห้ามมี เช่น BOT_CAPABILITIES อธิบายขอบเขตและข้อจำกัดจริง UNKNOWN ไม่แต่งข้อมูล และ HELP ไม่สัญญาว่าช่วยเฉพาะทางได้ การตรวจ keyword คำเดียวอาจผ่านข้อความที่ปฏิเสธความหมายเดิม

## 10. Regression Engineering Strategy

### ระดับการทดสอบ

| ระดับ | ขอบเขตและหลักฐานที่ต้องการ |
| --- | --- |
| Unit | ตรวจ Input policy, matching representation, candidate eligibility, selection tie และ result validation ด้วย expected ที่กำหนดไว้ |
| Integration | ตรวจลำดับ Validation → Matching → Selection → Response และ mapping exception ผ่าน Adapter เมื่อมีจริง |
| End-to-end Behavioral | เรียก Engine ผ่าน Python Interface จริงด้วยข้อความสมมติ ตรวจ Intent, Response และ rule_id รวมถึง CLI เฉพาะเมื่อมีในขอบเขต |
| Regression | เก็บข้อกำหนดและตัวอย่างที่แก้แล้วแบบ versioned และรันซ้ำทุกครั้งที่เปลี่ยนกฎ |
| Robustness | ตรวจ malformed type/text, long inputs และข้อผิดพลาดในขั้นภายใน พร้อมตรวจว่าไม่มีผลค้างหรือเปิดเผย raw |
| Performance | วัด latency และ peak memory ในสภาพแวดล้อมที่กำหนด ใช้กรณี normal, fallback, worst-case และขอบเขตความยาว |
| Independent Evaluation | เจ้าของประเมินรุ่นที่ freeze นอก Workspace และ CI ปกติตาม protocol ที่อนุมัติ |

### รูปแบบ Case และการตรวจ Coverage

| Field | ข้อเสนอ |
| --- | --- |
| case_id / requirement_id | รหัสถาวร และ Requirement หนึ่งรายการหรือรายการหลักพร้อมอ้างเสริม |
| input | ค่า str แบบ reversible escapes หรือ typed fixture สำหรับ Python-only values |
| expected_outcome | result หรือ exception ซึ่งแยก schema กัน |
| expected_intent / expected_behavior | ใช้สำหรับ outcome=result ระบุข้อจำเป็นและข้อห้ามของคำตอบ พร้อม expected_rule_id เมื่อตกลง |
| expected_exception | ใช้สำหรับ outcome=exception ระบุ exception type และเหตุผลที่ตรวจได้ ละ intent/behavior |
| category / rationale / severity / introduced_in | หมวด หลักฐานความเสี่ยง ระดับ และรุ่นที่เพิ่ม |
| source_sample_id / contract_version | อ้าง Development sample เมื่อมีที่มา และ version ของ Contract ที่ใช้ตัดสิน |

ตัวอย่างในเอกสารสำหรับ result ใช้ DEV-V01-026 → UNKNOWN, Rubric B7, BC-INT-07 ส่วน exception ใช้ None → TypeError, BC-IN-01 หลังอนุมัติ นับ coverage จาก Requirement ที่มีกรณี Positive, Negative, Boundary และ Failure Path ตามที่เกี่ยวข้อง ห้ามนับเคสที่รอคำตัดสินเป็น coverage ผ่าน ตรวจความครบจาก Requirement → Case ID → Test Method → ผลรัน และย้อนจาก Test กลับ Requirement จัดทำรายการ Requirement ที่ยังไม่ได้ทดสอบแยกจากร้อยละ coverage

Metamorphic Testing เสนอเติม whitespace รอบกรณีที่ Contract อนุญาต ภายในขอบเขต token/length เดิม แล้วเทียบทั้งสาม field การแก้คำปฏิเสธหรือเพิ่มคำอ้างเป็นคู่เปลี่ยนความหมายที่ต้องกำหนด oracle แยก Property-based Testing เริ่มจากชุด finite สำคัญและตัวสร้างด้วย Standard Library เช่น seed คงที่และ sampling จากกลุ่ม Unicode บันทึก seed, สูตรสร้าง, เวอร์ชัน และตัวอย่างที่พบเพื่อนำไปลดให้เล็กและทำเป็น Regression ถาวร ยังไม่เลือก Library เพิ่ม

Invariants ที่ตรวจได้คือ Result เท่ากันเมื่อ Input/config/version เท่ากัน, Intent อยู่ใน Taxonomy, padding ที่อนุญาตไม่เปลี่ยนผล, คำตอบไม่อ้างความสามารถที่ยังไม่มี และ Fallback ไม่ปกปิด Internal Error ยืนยันผลจาก Engine จริงใน Implementation Branch โดย freeze expected cases ก่อนแก้กฎ รัน RED และบันทึก command, exit, count และเหตุที่ล้มเหลว แยกการ import ไม่ได้ออกจาก failure ของ assertion จากนั้นทำให้ผ่านและรัน suite ทั้งหมดซ้ำ ตรวจ mandatory case IDs ที่รันจริงและตัด skipped, expected failures และ mock AI ออกจากผลยืนยันพฤติกรรม ครอบคลุมข้อเท็จจริงว่า Runner เดิมอาจคืน 0 แม้บางกรณีถูก skip หรือเป็น expected failure

## 11. Evaluation Strategy

| ชุด | หน้าที่และการควบคุม |
| --- | --- |
| Development Dataset | ปรับกฎ วิเคราะห์ FP/FN และเปรียบเทียบตัวทดลองบนชุดที่ทีมรู้จัก จัดกลุ่มรูปแปรตามต้นทางเมื่อเพิ่มชุด |
| Regression Cases | ตรึงพฤติกรรมที่อนุมัติกับกรณีปัญหาที่แก้แล้ว ใช้ Requirement ID และเก็บเหตุผลเมื่อ Contract เปลี่ยน |
| Robustness Cases | ทดสอบชนิดผิด รูป Unicode ผิดเงื่อนไข ความยาว และข้อผิดพลาดของระบบ รายงานผลแยกจาก Intent Accuracy |
| Held-out Evaluation | เจ้าของกำหนด protocol และเก็บชุดนอกพื้นที่เข้าถึงของ Agent กับ CI ตรวจซ้ำข้ามชุดตามกระบวนการที่เจ้าของควบคุม Freeze Engine/Contract และเกณฑ์ก่อนประเมิน รายงานผลรวมที่ได้รับอนุญาต |

Intent Accuracy = Intent ตรง Label / ตัวอย่างที่มี Label ในชุดที่ระบุ รายงาน confusion matrix, support ราย Intent และจำนวน engine errors แยก วางเกณฑ์นับ error ล่วงหน้า เสนอให้นับเป็นทำนายผิดในตัวหารเดิมเพื่อไม่ให้คะแนนสูงเพราะประมวลผลไม่ได้ Response Correctness = คำตอบผ่าน Rubric / จำนวนกรณีที่ต้องได้คำตอบ กำหนดวิธีนับคำตอบขาดหรือ Internal Error ล่วงหน้า และรายงาน Intent/Response ผ่านร่วมกันด้วย Regression Pass Rate = mandatory cases ผ่าน / mandatory cases ที่กำหนด พร้อมรายงาน failure/error/skip/missing แยก ผล Automated Tests วัดความสอดคล้องของข้อกำหนดที่ทดสอบ ผล Development วัดชุดที่ทีมเห็นแล้ว

เก็บ Dataset v0.1 และ Baseline Report เดิม ใช้ 12.5% เป็น Reference Intent Accuracy ของ Always-UNKNOWN บนชุดนี้ เสนอ acceptance criteria ตามความสำคัญ เช่น invalid input แยกจาก EMPTY_INPUT และการไม่อ้างความสามารถที่ยังไม่มีเป็นกรณีบังคับ ตรวจผลรายหมวดที่เสี่ยง เช่น False Match จากการปฏิเสธ และกำหนดวิธีรับมือเมื่อข้อมูลไม่พอ เกณฑ์เชิงตัวเลขสำหรับ release รอ error profile, support รายชนิด และการอนุมัติก่อน independent evaluation

## 14. Proposed Decisions

- รักษา Taxonomy เดิม รับ input หนึ่งข้อความ และถือ scope ของคำปฏิเสธ ผู้ถูกกล่าวถึง และวัตถุคำขอเป็นหลักฐานประกอบการเลือก สนับสนุนการงดเลือกด้วย UNKNOWN เมื่อไม่พอ
- ให้ Runtime แยก invalid type, invalid text และ Internal Error จาก Intent ปกติ ใช้ raw code points เป็นตัวเลือกตั้งต้นในการกำหนดความยาวหลังทดลอง
- ให้ rule_id มีความหมายคงที่และตรวจจากกฎผู้ชนะ ใช้ Rubric ที่ตรวจทั้งสิ่งที่ต้องตอบและสิ่งที่ห้ามอ้าง
- แยกการวัด Intent, Response, Regression และ Performance พร้อมผูก Requirement ID กับกรณีและผลรัน สถานะของข้อเสนอและข้อที่อนุมัติแล้วระบุใน §13

## 15. Research Roadmap สำหรับ TASK-005-R1

รายการด้านล่างเป็นแผนจาก Analysis Phase ส่วน TASK-005-R1 ดำเนิน EXP-001–004 ตามขอบเขต Text Processing การเปรียบเทียบวิธีเลือก Candidate ในข้อ 3 ยังรอการอนุมัติ [ผลการทดลอง TASK-005-R1](v0.1-thai-text-processing.md)

1. **กำหนด oracle และชุดทดลองก่อนรัน** ใช้ตัวอย่างสมมติหรือ Development ที่อนุญาต ตรึงรายการคู่ canonical/compatibility, Thai/Latin, quotation, negation, Emoji/Invisible และ near-miss แยกคู่ที่ควรเท่า คู่ที่ต้องต่าง และคู่ที่รอเจ้าของตัดสิน ระบุ version, count และ SHA-256 เมื่อมี dataset ที่ได้รับอนุมัติ
2. **เปรียบเทียบ Text Operations ทีละปัจจัย** ใช้ Raw เป็น control เทียบ trim, trim+NFC, trim+NFKC และเพิ่ม casefold/collapse/punctuation แบบแยกปัจจัยตามแผน วัดคู่ที่ควรรวมแล้วรวมได้ คู่ที่ต้องต่างแต่ชนกัน การเปลี่ยนตำแหน่ง และความยาวที่ขยาย ให้ตรวจรายหมวด ตัวอย่างภาษาพูด/segmentation ใช้การเทียบหน่วยที่กำหนดล่วงหน้าก่อนเลือกอัลกอริทึม
3. **เปรียบเทียบการเลือก Intent จาก Candidate ที่ระบุด้วยมือ** ใช้ตัวอย่าง §8 และ case variants จัดชุด Candidate/หลักฐานโดยคน ประเมิน First Match, Explicit Priority, Specificity และ Fallback โดยไม่ใช้ผลนี้อ้าง Accuracy ของ Engine บันทึก ties, คู่ที่ priority ไม่ครอบคลุม และเหตุผลที่ผู้ทบทวนเห็นต่าง
4. **วัดต้นทุนตามความยาว** ใช้ Python 3.14.8/Darwin arm64 ระบุ UCD, ข้อมูล, seed และขนาด ใช้ perf_counter_ns สำหรับเวลาและ tracemalloc สำหรับ Python allocations แยกรอบเพื่อเลี่ยง overhead หากต้องวัด RSS ให้ระบุเครื่องมือกับหน่วยแยกต่างหาก Sweep ความยาวของ ASCII/ไทย/emoji/combining marks/whitespace และกรณีขยาย รายงาน warm-up, รอบซ้ำ, median/tail และ peak แสดงความแปรปรวน และระบุให้ชัดว่านี่เป็นตัวเลขของ primitives ก่อนวัด end-to-end เมื่อมี Engine
5. **ปิดประเด็นตามหลักฐาน** สรุปการเปลี่ยน representation, collisions, ข้อผิดพลาดรายหมวด, ผลทรัพยากร และทางเลือกที่ยังเทียบไม่ได้ ส่งให้เจ้าของเลือก policy และปรับแผนก่อนเปิด Implementation Branch งานวิเคราะห์นี้สิ้นสุดที่แผนทดลอง
